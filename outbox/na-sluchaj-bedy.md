# На случай беды

Эту бумагу читают, когда всё сломалось. Она написана так, чтобы её можно было
распечатать и держать в столе. Ни одной команды здесь нет без объяснения, что
она делает.

Дата составления: 05.08.2026.

---

## Сначала — три вещи, которые нужно знать до всякой беды

**1. Станок — это не одна вещь, а четыре, и лежат они в разных местах.**

| Что | Где лежит | Пропадёт ли, если сгорит компьютер |
|---|---|---|
| **код станка** и все бумаги | папка `E:\Stanok` **и** хранилище GitHub | нет: есть наверху |
| **ящик отправки** с отчётами | там же **и** на сайте пульта | нет: есть наверху |
| **настоящие выписки** | только папка `E:\Stanok\corpus` | **да** |
| **журналы запусков** | только папка `E:\Stanok\runs` | **да** |

Две нижние строки — единственное, что нигде не дублируется, и это сделано
нарочно: настоящие документы клиентов наружу не уходят никогда. Цена этого
решения — они не защищены от гибели диска ничем, кроме вашей собственной копии.

**2. Наверху лежит два хранилища, а не одно.**

* `github.com/lordrubano/stanok` — сам станок. Закрытое.
* `github.com/lordrubano/stanok-pult` — пульт и ящик отправки. Открытое, из него
  собирается сайт.

**3. Раз в какое-то время делайте офсайт-копию.** Это одна команда, и что она
делает — написано в самом конце этой бумаги, в разделе «Как не доводить до
беды».

---

## Беда первая: погиб диск E

### Что уцелело

* **весь код станка** — он в GitHub, до последнего отправленного изменения;
* **все отчёты и состояние** — они и в GitHub, и на сайте пульта;
* **реестр шагов** — там же;
* **чертёж и план** — там же.

### Что потеряно навсегда

* **настоящие выписки** из папки `corpus`, если у вас нет их копии в другом
  месте. Восстановить их можно только одним способом: взять у того, кто их дал
  в первый раз;
* **журналы запусков** из папки `runs`. Это цепочка записей, скреплённая
  хешами; заново её не собрать даже теми же документами, потому что она
  описывает то, что уже произошло;
* всё, что было сделано **после последней отправки** в GitHub.

### Что делать первым

**Шаг 1.** Возьмите любой компьютер с интернетом. Установите на него две вещи:

* Git — программа, которая умеет забирать код из GitHub;
* Python версии 3.12 или новее — язык, на котором написан станок.

**Шаг 2.** Заберите станок из хранилища. Откройте командную строку и наберите:

```
git clone https://github.com/lordrubano/stanok.git E:\Stanok
```

Эта команда скачивает всё содержимое хранилища `stanok` в папку `E:\Stanok`
вместе со всей историей изменений. Ничего никуда не отправляет, ничего не
портит.

**Шаг 3.** Заберите пульт:

```
git clone https://github.com/lordrubano/stanok-pult.git E:\Stanok_public
```

То же самое, но для второго хранилища — того, из которого делается сайт.

**Шаг 4.** Приготовьте станку рабочее место:

```
cd E:\Stanok
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Первая строка переходит в папку станка. Вторая заводит для него отдельный
уголок, чтобы он не мешался с остальными программами на компьютере. Третья
доставляет из интернета те чужие библиотеки, которые станку нужны для работы.

**Шаг 5.** Убедитесь, что станок цел:

```
.venv\Scripts\python.exe -m pytest -q
```

Эта команда прогоняет все проверки станка — сегодня их около полутора тысяч.
Она ничего не меняет: только смотрит и считает. В конце должно быть написано
`N passed` и ни одного `failed`. Если так — станок цел полностью.

**Шаг 6.** Положите обратно свои выписки в папку `E:\Stanok\corpus`, если они у
вас где-то сохранились. Станок их туда не вернёт: он их никогда никуда не
отправлял.

## Беда вторая: потерян доступ к GitHub

Сюда относится всё сразу: забыт пароль, потерян телефон с подтверждением,
заблокирован ключ доступа, закрыт сам GitHub.

### Что уцелело

* **всё, что лежит на диске E** — папка `E:\Stanok` полна и работоспособна. В
  ней лежит не только сегодняшнее состояние, но и вся история изменений: она
  хранится внутри самой папки, в скрытом каталоге `.git`, а не на GitHub. GitHub
  — это копия, а не оригинал;
* **сайт пульта** продолжает работать, пока GitHub жив: он собран и лежит там.

### Что потеряно

* **возможность отправлять новое наверх** — и, значит, публиковать отчёты:
  публикация идёт через GitHub;
* **резервная копия наверху перестаёт пополняться**. Сама она никуда не
  девается, но новое туда не попадёт.

### Что делать первым

**Шаг 1.** Прежде всего убедитесь, что оригинал цел. Наберите:

```
cd E:\Stanok
git log --oneline -5
```

Эта команда показывает пять последних изменений с их короткими описаниями. Если
она их показала — история на месте, ничего не потеряно, беда только в связи с
GitHub.

**Шаг 2.** Немедленно сделайте копию, пока разбираетесь с доступом:

```
.venv\Scripts\python.exe offsite\offsite.py make D:\kopii\stanok-2026-08-05
```

Здесь `D:\kopii\stanok-2026-08-05` — **папка**, куда положить копию; она
создастся сама. Внутри появятся два файла: `STANOK_COPY.zip` (сам архив) и
`STANOK_COPY.sha256` (лист отпечатков, по которому копию потом проверяют).
Настоящие выписки и журналы запусков команда **не берёт никогда** — это записано
в самой программе и не настраивается. Место можно указать любое: флешка, второй
диск, папка облака. Занимает это около четырёх секунд, архив выходит примерно
на 3 мегабайта.

**Шаг 3.** Проверьте, что копия годная:

```
.venv\Scripts\python.exe offsite\offsite.py check D:\kopii\stanok-2026-08-05\STANOK_COPY.zip
```

Обратите внимание: здесь указывается **сам файл архива**, а не папка. Команда
распаковывает его в отдельное временное место, сверяет каждый файл по отпечатку
и собирает из восстановленной копии пульт. В конце она должна написать:
«Восстановление подтверждено: копия целая, политика соблюдена, станок из копии
собирается и показывает тот же реестр». Наличие архива само по себе ничего не
доказывает — доказывает только эта проверка.

**Шаг 4.** Восстанавливайте доступ к GitHub своими обычными средствами. Если
доступ вернуть нельзя совсем — заведите новое хранилище и скажите станку, куда
теперь отправлять:

```
git remote set-url origin <адрес нового хранилища>
git push -u origin master
```

Первая строка меняет адрес, по которому станок отправляет наверх. Вторая
отправляет туда всё, что накопилось, вместе с историей.

## Беда третья: испорчен реестр

Реестр — файл `E:\Stanok\registry\registry.csv`. В нём одна строка на каждый из
77 шагов плана: номер, фаза, сложность, состояние, название и примечание. Из
него собирается пульт.

### Что уцелело

**Всё.** Реестр — обычный текстовый файл под учётом истории, и его прошлое
хранится в 71 сохранённом изменении. Испортить его насовсем можно только
одновременно с гибелью всей папки, а это уже беда первая.

### Что делать первым

**Шаг 1.** Посмотрите, что именно испортилось:

```
cd E:\Stanok
git diff registry\registry.csv
```

Эта команда показывает построчно, чем нынешний файл отличается от последнего
сохранённого. Ничего не меняет.

**Шаг 2.** Если изменения не нужны — верните файл как был:

```
git checkout -- registry\registry.csv
```

Эта команда возвращает файл к последнему сохранённому виду. **Она стирает все
несохранённые правки в этом файле** — поэтому сперва шаг 1.

**Шаг 3.** Если испортилось раньше и уже сохранилось, посмотрите историю
именно этого файла:

```
git log --oneline -- registry\registry.csv
```

Команда покажет список изменений, где реестр трогали, самое свежее сверху. У
каждого слева стоит короткий код вида `a1b2c3d`. Выберите то, где реестр был
ещё цел, и возьмите файл оттуда:

```
git checkout a1b2c3d -- registry\registry.csv
```

Здесь `a1b2c3d` — тот самый код из списка. Команда берёт файл из выбранного
момента и кладёт на место нынешнего.

**Шаг 4.** Соберите пульт заново:

```
.venv\Scripts\python.exe pult\build.py
```

Эта команда читает реестр и собирает из него страницу пульта. Если в реестре
осталась ошибка — она откажется работать и скажет, в какой строке беда. Это
не поломка, а защита: пульт с испорченным реестром хуже, чем несобранный.

## Беда четвёртая: не запускается арбитр

**Скажу прямо: арбитр в станок не входит.** Я проверил поиском по всему коду —
у станка нет от арбитра ни одной зависимости. Арбитр живёт в соседнем проекте,
в папке `E:\AI_Projects`, и относится к нему.

### Что это значит для станка

* **станок работает без арбитра полностью**: разбор документов, проверки,
  выгрузка в Excel, отчёты, публикация — ничего из этого арбитра не спрашивает;
* **ничего не теряется**, пока арбитр не работает;
* **делать в станке ничего не нужно**.

### Что делать первым

Если под арбитром имеется в виду что-то из соседнего проекта — его восстановление
описывается бумагами того проекта, не этой. Если же под арбитром имеется в виду
что-то, чего я в станке не нашёл, — скажите, и я допишу этот раздел
по-настоящему, а не по догадке. Писать наугад в бумаге, которую читают в беде,
нельзя: неверный совет в такую минуту хуже, чем никакого.

## Что не восстанавливается ничем

Это главный раздел бумаги. Всё остальное так или иначе чинится; перечисленное
здесь — нет.

**1. Настоящие выписки из папки `corpus`.** Они никогда никуда не отправлялись
и не отправятся: это решение принято сознательно и защищено проверками, которые
останавливают публикацию, если документ случайно попал в ящик отправки. Обратная
сторона: единственная их копия — та, что на диске. Если диск погиб, а своей
копии нет, взять их можно только у того, кто дал их в первый раз.

**2. Журналы запусков из папки `runs`.** Это цепочка записей, где каждая
скреплена с предыдущей отпечатком. Она описывает то, что уже произошло:
какой документ, когда, чем, с каким итогом. Прогнать документ заново можно —
получить прежний журнал нельзя, это будет журнал нового прогона.

**3. Работа, сделанная после последней отправки наверх.** Пока изменения не
отправлены в GitHub, они существуют в одном экземпляре — на диске.

**4. Тайный ключ подписи, когда он появится.** Сегодня его ещё нет: ключевую
пару вы не заводили. Когда заведёте — знайте: потеря тайного ключа означает,
что подписывать новые выпуски прежним ключом больше нельзя. Уже выданные
подписи останутся проверяемыми, но новый ключ придётся раздать заново всем, кто
проверяет. Ключ нельзя восстановить ни из чего: он не выводится ни из изделия,
ни из открытого ключа. Хранить его надо отдельно от станка и отдельно от
компьютера, на котором станок работает.

**5. Пароль от GitHub, если нет второго способа входа.** Это беда не станка, но
она отрезает от резервной копии.

## Как не доводить до беды

Три вещи, каждая занимает минуту.

**Раз в неделю — офсайт-копия:**

```
cd E:\Stanok
.venv\Scripts\python.exe offsite\offsite.py make D:\kopii\stanok-YYYY-MM-DD
```

Вместо `YYYY-MM-DD` поставьте сегодняшнее число, чтобы копии не затирали друг
друга. Куда класть — решайте сами: второй диск, флешка, папка облака. Настоящие
выписки и журналы в копию не попадут никогда.

**Сразу за ней — проверка копии:**

```
.venv\Scripts\python.exe offsite\offsite.py check D:\kopii\stanok-YYYY-MM-DD\STANOK_COPY.zip
```

Копия, которую не проверяли, копией не считается.

**Отдельно и своими руками — копия папки `corpus`.** Её станок не копирует
никуда и не будет. Скопируйте её на флешку или во внешний диск обычным
перетаскиванием. Это единственное место, где ручная работа необходима, и
причина у неё та, за которую вы платите: настоящие документы клиентов машина
наружу не отдаёт даже вам в облако, если вы её об этом не попросили.

  языком написано, что сделано и что осталось.

  со всеми отчётами.

только одно: потеря того, что нигде не продублировано. Поэтому раздел «что не
восстанавливается ничем» стоит читать не в беду, а сегодня.
