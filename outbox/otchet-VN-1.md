# Отчёт: чтение ящика без кеша раздатчика страниц

Работа вне нумерации. Дата: 03.08.2026.

## Что было не так

Опись ящика отдавалась через сайт, а сайт кеширует страницы на десять минут —
и не только у читателя в браузере, но и у самого раздатчика. Файл уже лежит в
хранилище, а наружу ещё десять минут идёт прежний, без единого признака, что он
несвежий. Наблюдатель слеп и знать об этом не может.

Заголовками сайта станок не управляет. Побороть этот кеш нельзя.

## Что сделано

Кеш вреден не сам по себе. Он вреден потому, что адрес указывал на **ветку**, а
её содержимое меняется: один и тот же адрес вчера и сегодня означает разное, и
лежалый ответ неотличим от свежего.

Если адресовать по **коммиту**, содержимое неизменно. Тогда кеш безвреден:
ответ либо тот самый, либо его нет вовсе. Третьего не дано.

Живой номер коммита даёт `git ls-remote` — он спрашивает сам сервер и не
кешируется ничем. Это единственная величина в цепочке, про которую точно
известно, что она свежая. Всё остальное читается уже по ней.

Дорога чтения целиком:

```
# 1. Живой номер коммита
git ls-remote https://github.com/lordrubano/stanok-pult.git main

# 2. Опись со всеми хешами — по этому номеру
curl https://raw.githubusercontent.com/lordrubano/stanok-pult/<коммит>/outbox/opis.json

# 3. Любой файл — по тому же номеру
curl https://raw.githubusercontent.com/lordrubano/stanok-pult/<коммит>/outbox/<имя>
```

Предела числа обращений на этой дороге нет, вход не требуется.

## Человек из цепочки убран

Прежде отпечаток описи станок сообщал владельцу, а владелец — наблюдателю. Это
и был человек в цепочке. Теперь его нет: публикация кладёт в ящик машинную опись
`opis.json` с именем, размером и SHA-256 каждого файла. Наблюдатель читает опись
и файлы по одному и тому же номеру коммита и сличает хеши сам. Верить на слово
не нужно никому, включая станок.

## Проверка делом

Не по имени файла и не по зелёному запуску.

1. Положен файл с неповторимым признаком внутри.
2. Отправлен.
3. Сразу прочитан снаружи по живому номеру коммита.
4. Сличены байты: **прочитанное снаружи совпало с положенным побайтово**,
   `796d85b765cf…` с обеих сторон.
5. Тот же файл через сайт в тот же момент отвечал `404` — то есть прежняя
   дорога отставала ровно так, как и было сказано.

Оба рубежа защиты проверены заново после переделки:

* **рубеж отправки** — подложены копия из корпуса под безобидным именем и книга
  Excel: отправка встала, назвав обе причины, коммита не было;
* **рубеж публикации** — те же приманки пропущены мимо отправки силой: сборка
  упала красным, и снаружи приманок нет (обе дают `404`), машинная опись о них
  не знает.

## Ошибка, найденная и исправленная тут же

Первая работа подтверждения сверяла только те файлы, что лежат у меня, и не
смотрела на состав снаружи. Убранный файл остался бы висеть в открытом
хранилище, а подтверждение бодро сказало бы «всё сошлось» — каждый мой файл
ведь на месте. Нашлось это на пробном файле, который я же и убирал.

Теперь сверяется состав целиком: лишнее снаружи и недостающее снаружи — оба
случая дают отказ. Плюс сверяется, что машинная опись не расходится с самими
файлами.

## Чем это лучше прежнего

| | было | стало |
|---|---|---|
| дорога | страницы сайта | коммит в открытом хранилище |
| задержка | до 10 минут, невидимо | нет, адрес неизменен |
| кто ручается за свежесть | станок на словах | сам читатель по хешам |
| человек в цепочке | был | нет |
